# Как добавить банк

Новый банк — это YAML-профиль плюс фикстура для теста. Python-код обычно менять не нужно.

## 1. Снимите обезличенный снапшот страницы

Войдите в кабинет руками, запустите браузер с отладкой (`--remote-debugging-port=9222`) и выполните:

```bash
bank-collector --bank example --snapshot --out /tmp/bc
```

Рядом с отчётом появится `snapshots/*.html` и `*.txt`: из страницы вырезаны скрипты, значения
полей ввода, e-mail и длинные цифровые последовательности. Снапшот безопасно читать и показывать;
**не** публикуйте его целиком, если в нём остались имена контрагентов.

## 2. Найдите селекторы

Откройте снапшот в браузере и найдите:

- контейнер, который появляется только после прогрузки кабинета, — это `wait_for`;
- повторяющийся блок остатка — это `row` в `balances`;
- повторяющуюся строку операции — это `row` в `transactions`.

Селектор должен быть устойчивым: предпочитайте `data-testid`/`data-qa`/семантические роли, а не
хешированные классы вида `.sc-1x2y3z`.

## 3. Опишите профиль

```yaml
bank: mybank
status: verified          # unverified, пока числа не сверены глазами
url: "https://mybank.example/cabinet"
wait_for: "[data-testid=dashboard]"

balances:
  - row: "[data-testid=account-card]"
    fields:
      account:
        selector: "[data-testid=account-name]"
      amount:
        selector: "[data-testid=account-balance]"
        regex: "(-?[\\d\\s.,]+)\\s*₽"   # необязательно: вытащить число из текста
        group: 1

transactions:
  - row: "[data-testid=operation-row]"
    fields:
      date:
        selector: "[data-testid=operation-date]"
      amount:
        selector: "[data-testid=operation-amount]"
      payee:
        selector: "[data-testid=operation-payee]"
```

Правила:

- `fields` — словарь «имя поля → спецификация»; допустимы `selector`, `attr` (взять атрибут вместо
  текста), `regex` + `group` (вытащить фрагмент), `parse` (разобрать значение) и `optional`
  (не считать отсутствие элемента ошибкой).
- `parse: ru_date` превращает текст заголовка дня в ISO-дату `YYYY-MM-DD`: понимает `27 октября`,
  `27 октября 2025`, `Сегодня`, `Вчера` (регистр не важен), а хвост после даты — например итог дня
  `27 октября−1 234 ₽` — игнорирует. Если года нет, он выводится относительно даты запуска (тот же
  год, а если дата оказалась бы в будущем — предыдущий: `29 декабря` в октябре = прошлый декабрь).
  Неразобранный текст даёт `value: null`, исходная строка остаётся в `raw`, в `warnings` —
  `cannot parse ru_date from …`. Пока это единственное значение `parse`.
- `optional: true` — для полей, которых у части строк нет (описание операции, кэшбэк). Отсутствие
  элемента (или атрибута) даёт пустое поле без предупреждения на каждую строку. Для обязательных
  полей поведение прежнее: `selector matched nothing` в `warnings`.
- Деньги разбираются автоматически: `1 234,56 ₽`, `-1 234,56`, `1.234,56`, `1,234.56` дают
  `Decimal` с сохранённым знаком; исходная строка остаётся в `raw`, валюта — только если она есть в
  строке. Ничего не додумывается.
- Валидатор отклоняет профили с полями вида `password`, `token`, `cookie`, `sms` — инструмент не
  работает с секретами, и профиль не место, чтобы их протащить.
- `row` — обычный CSS, но с двумя оговорками, которые сильно помогают:
  - `:has(...)` работает и очень выручает, когда признак лежит не в самой строке, а рядом:
    `section[data-test-id^=product-view-component-]:has([data-test-id=product-view-amount])`
    берёт только настоящие продукты, пропуская рекламные блоки без суммы. Вложенность допустима:
    `div:has(> [data-date]):has(> button[data-test-id=operation-cell])`.
  - якорем лучше брать `[data-test-id=...]` / `[data-qa=...]`, а не хешированные классы вида
    `.sc-1x2y3z` — они меняются на каждом релизе фронтенда.

### Если остатки и операции на разных страницах

Раздел может попросить свою страницу: `url` и `wait_for` внутри записи переопределяют адрес
профиля. Драйвер откроет её сам и запишет в `source_urls`.

```yaml
url: "https://mybank.example/dashboard/"
wait_for: "[data-testid=dashboard]"

balances:
  - row: "[data-testid=account-card]"
    fields: { ... }

transactions:
  - url: "https://mybank.example/history/"
    wait_for: "[data-testid=operation-row]"
    row: "[data-testid=operation-row]"
    fields: { ... }
```

### Если операции сгруппированы по дням

Частая картина: дата стоит один раз на группу, а внутри группы несколько операций (так делает
Альфа). Тогда у записи есть `items` — строки внутри строки. Поля группы и поля операции
склеиваются в одну строку отчёта; если имя поля есть и там и там, побеждает операция и в
`warnings` появляется предупреждение.

```yaml
transactions:
  - url: "https://mybank.example/history/"
    row: "div:has(> [data-date])"          # группа = день
    fields:
      date:
        selector: "[data-date]"
        attr: "data-date"                  # берём атрибут, а не текст
    items:
      row: "button[data-test-id=operation-cell]"
      fields:
        title:
          selector: "[data-test-id=title-text_content]"
        amount:
          selector: "[data-test-id=transaction-status]"
```

В `items` нельзя вкладывать ещё `items` (валидатор отклонит): если у банка три уровня, это повод
сделать профиль проще, а не движок сложнее.

### Если лента плоская: заголовки дней и операции — соседи

Бывает наоборот: день — не обёртка, а такая же строка списка, как и операция (так устроен
Т-Банк). Тогда нужен блок `header`:

```yaml
transactions:
  - row: "ul > li"                        # ВСЕ строки ленты: заголовки и операции, по порядку
    header:
      selector: "[data-qa-type=atom-operations-feed-header]"   # чем заголовок отличается
      fields:
        date:
          selector: "[data-qa-type=atom-operations-feed-header]"
          parse: ru_date                  # "27 октября−1 234 ₽" -> 2026-10-27
    fields:
      title:
        selector: "[data-qa-type=atom-operations-feed-operation-title]"
      amount:
        selector: "[data-qa-type=atom-operations-feed-operation-amount]"
      description:
        selector: "[data-qa-type=atom-operations-feed-operation-description]"
        optional: true                    # не у каждой операции есть описание
```

Правила:

- `row` матчит все строки ленты. Строка, внутри которой найден `header.selector`, — заголовок:
  её `header.fields` становятся текущими значениями и в отчёт **не** попадают. Остальные строки
  читаются по своим `fields` и наследуют текущий заголовок; при совпадении имени поля побеждает
  поле операции, и в `warnings` появляется предупреждение.
- Вся лента читается одним заходом на странице (`snapshot_rows`), а строки затем упорядочиваются
  по своей вертикальной позиции: дата операции — ближайший заголовок **выше неё на экране**, а не
  предыдущий в порядке DOM (виртуализированный список может рисовать строки в другом порядке).
- Операции, оказавшиеся **выше** первого заголовка в данном проходе (по положению на экране),
  даты не имеют: они молча пропускаются и считаются в `scroll.headerless_rows`. При прокрутке
  виртуализированного списка заголовок может уехать из DOM раньше своих операций — эти строки
  уже прочитаны в прошлых проходах. Если список не прокручивается, такие строки просто теряются —
  проверьте, что первая строка ленты действительно заголовок.
- `header` и `items` вместе запрещены: это два способа описать одно и то же.
- `header` принимает только `selector` и `fields`; `fields` проверяются так же, как обычные поля
  (включая `parse` и `optional`).

### Если список догружается прокруткой

Многие кабинеты показывают 20–50 строк и **добавляют следующие, когда список прокручивают**.
Чтобы прочитать весь список, а не только первый экран, опиши в записи блок `scroll`:

```yaml
transactions:
  - url: "https://mybank.example/history/"
    row: "[data-testid=operation-row]"
    fields:
      date:
        selector: "[data-testid=operation-date]"
    scroll:
      max_rounds: 200                    # потолок шагов (целое >= 1, по умолчанию 50)
      step_px: 1200                      # пикселей за шаг (целое >= 100, по умолчанию 1500)
      settle_ms: 900                     # пауза после шага, ждём догрузки (целое >= 0, по умолчанию 800)
      stop_after_empty_rounds: 4         # стоп после стольких шагов без новых строк (>= 1, по умолчанию 3)
      stop_before_date: "2026-01-01"     # необязательно: стоп, как только встретилась дата раньше этой (сам этот день собирается целиком)
      load_more_text: "Показать ещё"     # необязательно: полный текст единственной кнопки догрузки (по умолчанию кликов нет)
      load_more_scope: "div:has(> button:not([data-test-id])):has(button[data-test-id=operation-cell])"
                                         # ОБЯЗАТЕЛЕН вместе с load_more_text: контейнер списка
      max_clicks: 100                    # потолок кликов по этой кнопке (целое >= 1, по умолчанию 100)
```

Правила:

- **Прокрутка — это чтение.** Двигается только вьюпорт: DOM не меняется, запросы от себя не
  отправляются, кнопка «скачать выписку» не трогается. Единственный клик — кнопка догрузки,
  названная в `load_more_text`. Она включается только вместе с `load_more_scope`: CSS-селектором
  контейнера списка. Без скоупа профиль отклоняется, скоуп без текста — тоже. В момент клика
  берутся только контейнеры скоупа, которые содержат хоть одну строку записи; их должно быть
  ровно один, иначе клика нет, предупреждение `load-more scope '…' matched N list containers,
  none clicked` и остановка с `stop: error` (код выхода `5`). Кнопка ищется только внутри этого
  контейнера, среди `<button>`, и нажимается, только когда прокрутка не добавила ни одной новой
  строки и её **весь** текст (без крайних пробелов, внутренние пробелы схлопнуты) **в точности**
  совпадает со строкой (регистр не важен; профиль может написать «показать ЕЩЁ»). Текст обязан
  входить в белый список (**только** «Показать ещё», «Показать еще») —
  «Скачать выписку», «Оплатить» и прочее отклоняются валидатором. Если таких кнопок нет — обычный
  пустой раунд; если больше одной — клика нет, предупреждение и остановка с `stop: error`.
  Кнопка с той же подписью вне списка (блок офферов) или не `<button>` (ссылка,
  `[role=button]`) не нажимается никогда: если прокрутка закончилась пустым раундом, а такая
  кнопка есть, пишется предупреждение и `complete` становится `false` (код `5`). Сама кнопка
  лишь дописывает строки списка; страницы перечисления не переключаются, другие кнопки не
  нажимаются. Клик и скоуп профиля `alfa` проверены на живом кабинете 26.10.2026 (один клик
  дописал 40 операций назад до 2025-11-01, `stop: date`, `complete: true`) — после первого живого
  запуска своего банка отметьте это в `notes` профиля.
- Блок `scroll` разрешён **только** у записи с `row` (иначе нечего считать — валидатор отклонит).
- Ключи и их значения проверяются: неизвестный ключ, не целое число, `true` вместо числа,
  отрицательное значение, пустая строка или не-строка в `load_more_text`, текст не из белого
  списка, `load_more_text` без `load_more_scope` (и наоборот), дата не формата `YYYY-MM-DD` —
  ошибка профиля.
- Драйвер останавливается, когда список перестал расти (`stop_after_empty_rounds`), когда
  появилась строка с датой раньше `stop_before_date`, когда исчерпан `max_rounds` или
  `max_clicks` (последние два попадают в `warnings`).
- Каждый клик по кнопке догрузки считается раундом и расходует `max_rounds`.
- Строки, которые кабинет повторяет при перерисовке, не дублируются: операция узнаётся по дате,
  названию, категории и сумме, и раунд добавляет строку, только если показывает такую операцию
  чаще, чем она уже собрана. Две одинаковые покупки за один день остаются двумя строками.
- Колесо крутится над серединой вьюпорта (указатель туда перемещается — это наведение, не клик),
  поэтому прокручивается и список со своим контейнером прокрутки.
- Отключить прокрутку можно на один запуск флагом `--no-scroll` или убрать блок `scroll:` из
  профиля.

## 4. Добавьте фикстуру и тест

Скопируйте `tests/fixtures/example_dashboard.html` в свою фикстуру, замените значения на
**синтетические** (реальные суммы и контрагенты в репозиторий не попадают) и добавьте тест по
образцу `tests/test_collect.py`: профиль → фикстура → ожидаемые остатки и операции.

## 5. Переключите статус

`status: unverified` → `verified` только после того, как вы сравнили числа в отчёте с тем, что
показывает кабинет. Непроверенный профиль, помеченный как проверенный, — худший вид бага: человек
верит цифрам. Промежуточный `draft` — разметка прочитана с живой страницы (селекторы и структура
сняты), но сквозной запуск со сверкой чисел ещё не сделан; так помечен `tbank`.

## Почему селекторы ломаются

Кабинеты переезжают на новые фронтенды, классы генерируются сборщиком, блоки переименовываются.
Симптом: `--bank` завершается кодом `4` и пишет `warnings` про пустые списки. Лечение: новый
снапшот → правка селекторов → тест с новой фикстурой. Поэтому профили держим данными, а не кодом.

## Необязательно: экран постоянного кода

Некоторые кабинеты (Альфа — так) вместо повторного входа просят **постоянный** «секретный код».
Если у банка такой экран есть, добавь в профиль секцию `unlock:` — её читает только
`bank-collector --enter-code`:

```yaml
unlock:
  markers: ["секретный код"]          # фразы, по которым экран узнаётся
  submit_text: ["Вперёд"]             # подпись кнопки отправки
  input_selector: 'form[class*="pincode"] input[type="password"]'
  success_wait: "[data-test-id=common-balance-button]"   # что видно после успеха
  code_file: "~/.config/bank-collector/<bank>-code"      # файл 0600
  max_attempts: 1                     # больше одного кода за запуск — никогда
  min_attempts_left: 3                # не вводить, если попыток меньше
  status: unverified
```

Правила те же, что и для остального профиля: селекторы бери со своего экрана, фикстуру — в
`tests/fixtures/`, тест — в `tests/test_unlock.py`. Код в репозиторий не попадает никогда.
